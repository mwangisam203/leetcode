NOTES: WHAT TO PAY ATTENTION TO

Choosing the right structure:

set — membership only, no values attached (contains duplicate, intersection)
dict — key → value mapping (two sum: value → index)
Counter (subclass of dict) — key → count, with useful extras (.most_common(), arithmetic between Counters)
defaultdict — dict that auto-initializes missing keys (group anagrams, adjacency lists) — avoids if key not in d: d[key] = [] boilerplate


How hashing achieves O(1):

A hash function converts a key into an array index. Average case O(1) for insert/lookup/delete because you go straight to the bucket.
Worst case is O(n) if every key collides into the same bucket — this matters when explaining complexity: say "O(1) average, O(n) worst case" not just "O(1)."
Python dicts resize and rehash automatically as they grow — you don't manage this yourself, but know that it happens (amortized O(1) insert accounts for occasional resize cost).


Collision handling (know this exists, even if you don't implement it often):

Separate chaining — each bucket holds a list/linked-list of entries (what example #10 does above)
Open addressing — on collision, probe for the next open slot (linear probing, quadratic probing, double hashing)
Python's dict uses open addressing internally, but separate chaining is what's usually expected when asked to "implement a hash map" in interviews — it's simpler to explain and code under pressure.

Common pitfalls:

Using a list where a set/dict would be O(1) — checking x in some_list is O(n); checking x in some_set is O(1). This is the single most common "why is my solution too slow" bug.
Forgetting mutable types (lists) can't be dict keys or set members — only hashable (immutable) types: strings, numbers, tuples of hashables.
Off-by-one on prefix sum problems — always double check the "empty prefix" seed case ({0: 1} in subarray sum).
Assuming dict insertion order doesn't matter — as of Python 3.7+, dicts preserve insertion order, and some problems rely on that.


INTERVIEW QUESTIONS THAT GET ASKED

Conceptual (expect these as follow-ups, not just "solve the problem"):

"What's the time complexity of dict/set operations, and why?" — answer: O(1) average via hashing, O(n) worst case via collisions.
"How would you implement a hash map yourself?" — see example #10; know separate chaining at minimum.
"What makes a good hash function?" — deterministic, uniform distribution across buckets, fast to compute, minimizes collisions.
"What happens when a hash table gets full?" — resizing/rehashing; mention load factor (entries / buckets) as the trigger, typically resized when load factor exceeds ~0.7.
"Why can't you use a list as a dictionary key?" — mutability breaks hashing (the hash would change if the list changed, but hash tables assume a key's hash is stable).

Coding (in rough order of frequency in interviews):

Two Sum (almost universal — often the warm-up question)
Contains Duplicate / Contains Duplicate II (within distance k)
Group Anagrams
Valid Anagram
Subarray Sum Equals K
Longest Consecutive Sequence
Top K Frequent Elements
LRU Cache (hash map + doubly linked list — a step up, very common at mid/senior level)
Design HashMap / Design HashSet (from scratch)
Word Pattern / Isomorphic Strings (bijective mapping between two hash maps)

Follow-up pressure questions to be ready for:

"Can you do this in O(1) space instead?" — often not possible with hashing (that's the tradeoff you're making: O(n) space for O(1) time), and it's fine to say so directly rather than forcing a bad answer.
"What if the input is a stream, not a fixed array?" — tests whether you understand incremental hashing (updating counts/sums as data arrives) vs. needing the full array upfront.


COMPLEXITY QUICK REFERENCE
Operation	Average	Worst case
dict/set insert	O(1)	O(n)
dict/set lookup	O(1)	O(n)
dict/set delete	O(1)	O(n)
Building a dict/set from n items	O(n)	O(n²)
set union / intersection	O(min(n, m)) roughly	O(n·m)

The "worst case O(n)" only shows up with pathological hash collisions — in practice and in almost all interview contexts, say O(1) and mention worst case only if asked to be precise.

DICT vs LIST FOR COUNTING
- list: ordered values only, no key-to-value pairing → wrong tool 
  for "count how many times X appears"
- dict: key-value pairs → perfect for "map each character to its count"
- collections.Counter: a dict subclass built specifically for counting; 
  Counter(string) instantly gives {char: count} for every char.
- Counter also supports subtraction: Counter(s) - Counter(t) tells you 
  what's left over after cancelling matching counts — empty result 
  means the counts fully matched.
