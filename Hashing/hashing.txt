HASHING: CHOOSE WHAT THE KEY MUST REMEMBER

1. MATCH THE STRUCTURE TO THE QUESTION

set: "have I seen this value?" Store membership only.
dict: "where/when did I see it?" Store value -> index or prefix -> earliest index.
Counter: "how many times?" Store value -> frequency.
defaultdict(list): "which items belong together?" Store signature -> group.

x in a list scans up to n items; x in a set/dict is average O(1).
Building a table is typically average O(n) time and O(u) space for u distinct keys.
Keys must be hashable, and their hash/equality behavior must remain stable while
stored. A tuple works only if its contents are hashable; ([1],) is still invalid.
Hash equality alone does not prove key equality: different keys may collide.

2. TWO SUM: LOOK UP BEFORE STORING

nums = [3, 3], target = 6
index 0: complement 3 is absent; store {3: 0}.
index 1: complement 3 is present; return [0, 1].
Invariant: seen contains only earlier indices, so the same element is never used
twice. [3] with target 6 must return [], not [0, 0].

For count_sum_pairs, store counts rather than one index: [1, 1, 1], target 2 has
three INDEX pairs, (0,1), (0,2), (1,2). A set cannot represent that multiplicity.
first_repeated_value returns the earliest second encounter: [1, 2, 2, 1] -> 2.
This differs from finding the earliest first occurrence among repeating values.

3. GROUP ANAGRAMS: STORE AN EXACT SIGNATURE

Sorted characters: "eat", "tea", "ate" -> "aet".
26-count tuple: positions represent a through z, so this requires lowercase ASCII.
Unicode frequency signature: frozenset(Counter(word).items()) handles arbitrary
characters. Matching remains case-sensitive and compares exact code points;
visually equivalent Unicode spellings are not normalized automatically.

A list of counts is mutable and cannot be a key; tuple(counts) can be.
Group by the signature itself, not just hash(signature), because hashes collide.
A set of characters loses counts: "ab" and "aab" are not anagrams.
Counter('a') - Counter('aa') is empty because subtraction drops nonpositive counts.
Use Counter(s) == Counter(t) to check frequency equality.

4. PREFIX SUMS: THE TABLE'S VALUE CHANGES THE QUESTION

For subarray_sum, prefix[j] - prefix[i] == k implies prefix[i] == prefix[j] - k.
Store counts of previous prefixes to count ALL matching intervals.
Seed {0: 1} so a subarray starting at index zero can match the empty prefix.

Trace nums=[1, -1, 1], k=1 (read a match before storing the current prefix):
value    running prefix    prior count of prefix-k    total matches
1        1                 seen[0] = 1                1
-1       0                 seen[-1] = 0               1
1        1                 seen[0] = 2                3

Recording the prefix before querying wrongly counts an empty interval for k=0.
For longest_zero_sum_subarray, store the EARLIEST index, seeded {0: -1}; repeated
prefixes bound a zero-sum interval, and the earliest index gives maximum length.
For subarrays_divisible_by_k, count matching prefix remainders instead of exact
prefix values. This repo requires positive k. Negative array values are supported.

5. TOP K: FREQUENCY IS THE BUCKET INDEX

n = len(nums), u = len(set(nums)); these count different things.
For [1, 1, 2, 2, 3], n=5 and u=3. This repo accepts 0 <= k <= u.
A number's frequency is at most n, so n+1 buckets cover frequencies 0 through n.
The implementation uses max(observed frequency)+1 to avoid unused upper buckets.
Stop immediately after appending the kth answer, INSIDE the inner loop.
Otherwise a tied bucket can grow the answer beyond k, so equality never succeeds.
Read ../docs/top-k-walkthrough.md for a complete trace and the ten-number example.

6. COLLISIONS, GROWTH, AND SPACE

MyHashMap uses separate chaining: each bucket holds a list of key/value pairs.
Two unequal keys can land in the same bucket; scan and compare keys within it.
Updating an existing key changes its value without increasing the entry count.
len(table) counts entries; table.size counts buckets. These are different sizes.
Load factor = entries / buckets. This implementation doubles capacity above 0.75
and rehashes every entry, because hash(key) % capacity changes with capacity.
Deletion does not shrink capacity. Missing get returns -1, so it cannot distinguish
an absent key from a stored -1 value; this follows the exercise's API.

Lookup/removal are expected O(1) with a suitable distribution; insertion is
amortized expected O(1) across growth. Collisions can make an operation O(n).
Capacity b also matters: storage is O(n+b), not just O(n) for a mostly empty table.
Hashing trades memory for faster lookup; an O(1) lookup does not make the entire
algorithm O(1). A scan of n items still takes at least O(n) time.

7. VARIABLE-SIZE WINDOWS: SHRINK UNTIL VALID

longest_unique_substring_length keeps a set representing text[left:right+1].
Before adding a repeated character, remove leftmost characters until it is absent.
Use while, not if: in "abba", the second b requires removing both a and b.
After adding the new character, every character in the window is unique.
Update the best length with right-left+1. This counts contiguous characters;
the set of all distinct characters in the entire string is not the answer.
For "pwwkew", the answer is 3 ("wke"), not 4 ("pwke" skips a position).
Each character enters and leaves once, so the nested while still costs O(n)
average time overall. Python code points are counted, not visual grapheme clusters.
